# 註解審查準則

適用於這個 repo 的 .py。審查對象只有「這一輪新增或修改」的註解與 docstring，
不要去翻既有的內容。

兩條準則：

1. 讀 code 的人有 ADHD。三行講不完的註解就是太長。
2. 業界常識不要寫。

## 判為問題（回報，指出行號與該怎麼改）

- 註解只是把下一行程式碼換句話說

      # 計數器加一
      counter += 1

- docstring 只是把函數名稱翻成一句話

      def cancel_order(...): """取消訂單。"""

- 解釋「這個技術本身是什麼」，而不是「這裡為什麼這樣用」

      # FOR SHARE 是共享鎖，彼此不互斥                      <- 常識，刪掉
      # 用 FOR SHARE 而不是 FOR UPDATE，否則同一場活動的
      # 購票會被序列化                                      <- 專案決策，留著

  同類的還有：lazy load 是什麼、joinedload 會讓列複製、transaction 是什麼、
  factory 模式是什麼、partial index 是什麼。

- 同一件事在多處各講一遍（class docstring 講過，method 又講一次）
- 三行還沒講到重點，或用三行講一行就講得完的事
- 中文註解重述英文程式碼的語意（例如 `# 建立 session` 之於 `session = make_session()`）

## 判為沒問題（放過）

- 專案特有的決策與代價：為什麼不採用另一種做法、踩過的坑、實測數字、這個假設
  什麼時候會失效。這些查不到，也看不出來。
- 提到名稱但補了資訊的。「Creates an unpublished event and clones the venue's
  layout」補了「未上架」與「複製場地」。
- 交叉引用與規格編號（"A8."）、TODO、章節標題（`# Cache`）、型別與 API 契約說明。

## 判準兩問

兩題都要過才算該留：

1. 刪掉之後，讀者會不會失去程式碼本身看不出來的資訊？不會 → 刪。
2. 這件事查官方文件或 Google 就有嗎？有 → 刪。

長度本身就是問題。一段有價值的「為什麼」寫成十行，一樣要砍到三行 —— 不是因為
它不重要，是因為沒人會讀完。拿不準的時候先看長度：三行以內就放過。

## 與腳本檢查的分工

`check_redundant_comments.py` 只抓字面重述（單行 docstring 扣掉函數名稱後的殘餘
資訊量、行註解與下一行的詞彙重疊），刻意不碰多行 docstring、語意層重述、中文註解
—— 那些需要判斷。這份準則涵蓋的正是那一半，不要重複腳本已經在做的事。
