app/ · 依賴原則

售票平台依賴地圖

這份文件只講一件事:這個 codebase 裡誰可以 import 誰,以及為什麼。 讀完你應該能在 code review 時一眼認出違規的 import,而不必先讀完整個 app/。

一條規則:依賴只往下

app/ 底下是一個嚴格的單向分層。上層知道下層的存在,下層對上層一無所知 —— 沒有任何 repository import service,也沒有任何 model import router。 整個 codebase 目前只有一條邊打破這個規則,已標在圖上。

每一層可以 import 什麼

下面每張卡片列的是實際的 import 行,不是抽象描述。 劃掉的那些不是風格建議,是這個架構賴以成立的界線 —— 破壞其中任何一條, 「一個 use case 一個交易」這個保證就不再成立。

routers/

只把 HTTP 翻譯成 use case 呼叫。不做判斷、不碰資料。

✓from app.services.event import EventService
✓from app.schemas.event import EventCreate
✗from app.models import Event
✗from app.repositories.event import …
services/

編排 use case。持有 aggregate,永遠不持有 session。

✓from app.repositories.event import …
✓from app.services.validators import …
✓from app.cache.event_layout import …
✗from sqlalchemy.ext.asyncio import AsyncSession
services/validators/

純粹的業務規則。呼叫端把狀態餵進來,它只負責判斷與拋例外。

✓from app.schemas.event import EventStatusInternal
✓from app.exceptions import EventPublishedError
✗from app.models import EventSeat
✗from app.db.redis import RedisClient
aggregates/

在交易內持有 session,提供狀態與變更操作 —— 但不做任何判斷。

✓from app.models import Event, EventSeat
✓from app.schemas.event import EventLayoutInternal
✗from app.services.validators import …
✗from app.repositories.event import …

為什麼要這樣切:交易邊界

分層不是為了整齊,是為了讓「讀狀態」和「依據該狀態的寫入」無法被拆散到兩個交易裡。 這個 codebase 是搶票系統,check-then-write 的競態會直接變成超賣。

做法是:repository 開啟交易並發出一個 aggregate,aggregate 在整個生命週期內持有那個 session。 service 拿到的是 aggregate,從來拿不到 session —— 所以它沒有辦法在交易外偷偷讀一筆資料。

兩種 DTO,不要搞混

schemas/ 底下住著兩個不同用途的家族。看後綴就知道它屬於哪一邊:

型別跨越的邊界誰在用
EventCreate
EventResponse		 HTTP ↔ 應用程式 router 的 request body 與 response_model。這是對外的公開契約,改動等於改 API。
EventLayoutInternal
EventOrderStatsInternal		 aggregate → service → validator 內部傳輸。永遠不會出現在 HTTP 上,所以可以自由改。它存在的理由是讓 validator 拿到的是明確的資料結構,而不是 ORM 列或 dict。

規則很簡單:ORM 列不准離開 aggregate。aggregate 對外一律回 *Internal, validator 因此不需要 DB 也能單元測試,mapper 則負責把 ORM 翻成對外 schema。

判斷與機制是分開的

這是最容易被無意破壞的一條。aggregates/ 和 services/validators/ 刻意各缺一半能力,誰也做不了對方的工作:

aggregate — 有 I/O,無判斷

它能讀能寫,但不知道什麼叫「可以上架」。它只提供 zone_pricings()、order_stats() 這類狀態,以及 publish()、soft_delete() 這類變更。

validator — 有判斷,無 I/O

它知道「每個分區都要有票價才能上架」,但自己拿不到票價 —— 必須由 service 餵進來。 因此它完全可以在沒有資料庫、沒有 Redis 的情況下被測試。

想在 aggregate 裡「順手」加一行 if not price: raise 時,請想起這個切法: 那一刻起規則就有兩個住處,而其中一個永遠測不到。

Redis 的寫入順序是不對稱的

Postgres 與 Redis 之間沒有兩階段提交,所以順序就是保證本身。 上架與下架的順序剛好相反,而且必須相反 —— 這是最容易寫反的地方。

已知的粗糙處

誠實列出來,免得你以為是自己看錯:

aggregates → repositories._pagination

唯一一條向上的 import。_pagination 是無狀態的純函式,實務上無害, 但若要徹底乾淨,它應該搬到 app/libs/ 之類的中性位置。

schemas → models

schemas/event.py import app.models,因為 *Internal DTO 直接內嵌了 Event / EventZone ORM 型別。 這讓「ORM 不外流」這條規則在型別層面留了一個縫 —— 是刻意的權衡(省掉一層轉換),不是疏忽。

containers.py import 幾乎所有東西

這是 composition root,本來就該如此 —— 它是唯一知道所有具體型別的地方, 其他每一層都只認得抽象的建構式參數。看到它的 import 清單很長,不要「順手整理」。

自己驗證一次

這些規則不是口頭約定,是可以用指令檢查的。接手後跑一次,確認它們還成立: 

# services 不該碰 session
grep -ln "AsyncSession\|sqlalchemy" app/services/*.py app/services/*/*.py

# validator 不該碰 model 或任何 I/O
grep -n "import" app/services/validators/event.py | grep -E "models|sqlalchemy|redis"

# 不該有任何反向依賴
grep -rn "from app.services\|from app.routers" \
  app/models app/schemas app/repositories app/aggregates app/db app/cache

# router 不該認得 model 或 repository
grep -n "app.models\|app.repositories\|app.aggregates" app/routers/*.py

# 印出完整的內部 import 圖
for f in $(find app -name "*.py" -not -path "*__pycache__*" | sort); do
  deps=$(grep -oE "^from (app[a-z_.]*|\.[a-z_.]*) import" "$f" \
         | sed 's/^from //;s/ import$//' | tr '\n' ' ')
  [ -n "$deps" ] && printf "%-38s -> %s\n" "$f" "$deps"
done

前四條目前都應該沒有任何輸出。有輸出就代表有人破壞了分層 —— 那不一定是錯的,但一定值得在 review 裡問一句為什麼。

依據 feature/init_db 分支的實際 import 關係繪製,所有不變式均以上述指令逐條驗證過。 測試現況:unit 37 + e2e 65 全數通過。
